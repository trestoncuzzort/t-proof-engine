# Upstream reports, drafted (NORTH-STAR.md target 4)

Each item is a kernel behaviour the matrix measured, written as the issue its project would want. **None is filed
yet:** filing is public and is the operator's call. Each needs its minimal reproduction run once more on the pinned
version (named below) before filing.

## 1. Boogie: `BadExprFromProver` on a CVC5 model that holds a Real value

- **Project:** github.com/boogie-org/boogie (as shipped in Dafny 4.11.0).
- **Measured:** PREDICT T22 (2026-10-07), receipt 04b99488c420. Running Dafny's verification with `--solver-path` set
  to CVC5, any failing proof whose model contains a real-typed value aborts with `BadExprFromProver` before reporting
  a verdict. The model text is CVC5's `0.0`.
- **Cause, as read:** the model converter has no case for a Real constant in CVC5's model syntax (Z3 prints reals as
  `(/ 0.0 1.0)` or an integer form that the converter does handle).
- **Minimal reproduction to confirm:** a Dafny method with a `real` parameter and a false postcondition, verified with
  CVC5. Expected: an error "postcondition might not hold". Observed: the exception.
- **Why it matters:** with CVC5, no failing proof that involves a real can be reported, so a second-solver check of
  Dafny programs over reals cannot see any failure.

## 2. Dafny: `/enhancedErrorMessages:0` overridden when counterexamples are bound

- **Project:** github.com/dafny-lang/dafny, 4.11.0.
- **Measured:** the same run. Binding the counterexample option sets `EnhancedErrorMessages = 1`, so the flag that
  would avoid model parsing cannot be turned off. CVC5 also refuses `produce-models=false` after initialization, so
  there is no other way around issue 1.
- **Minimal reproduction to confirm:** `dafny verify --solver-path cvc5 /enhancedErrorMessages:0` with the file from
  issue 1. Check whether the option takes effect.

## 3. GNATprove with Z3: monotonicity of rounding not found

- **Project:** github.com/AdaCore/spark2014. A question, not a bug.
- **Measured:** PREDICT T49 (rate_limit). With `r = prev + step` (Long_Float, `step >= 0`, all values bounded by 1e6),
  the postcondition `r >= prev - step` times out under `--prover=z3` at the matrix's step budget. It follows from the
  monotonicity of round-to-nearest.
- **Ask:** whether a lemma from SPARKlib's floating-point lemmas (`SPARK.Lemmas.Floating_Point_Arithmetic`) is the
  intended route, so t's SPARK lowering can cite it instead of timing out.
