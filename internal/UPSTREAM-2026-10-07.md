# Upstream reports, drafted (NORTH-STAR.md target 4)

Each item is a kernel behaviour the matrix measured, written as the issue its project would want. **None is filed
yet:** filing is public and is the operator's call. Each needs its minimal reproduction run once more on the pinned
version (named below) before filing.

## 1. Boogie: `BadExprFromProver` on a CVC5 model that holds a Real value

- **Project:** github.com/boogie-org/boogie (as shipped in Dafny 4.11.0).
- **Measured:** PREDICT T22 (2026-10-07), receipt 04b99488c420. Running Dafny's verification with `--solver-path` set
  to CVC5, any failing proof whose model contains a real-typed value aborts with `BadExprFromProver` before reporting
  a verdict. The model text is CVC5's `0.0`.
- **Cause, as read:** the model converter has no case for a Real constant in CVC5's model syntax (Z3 prints reals as
  `(/ 0.0 1.0)` or an integer form that the converter does handle).
- **Minimal reproduction to confirm:** a Dafny method with a `real` parameter and a false postcondition, verified with
  CVC5. Expected: an error "postcondition might not hold". Observed: the exception.
- **Why it matters:** with CVC5, no failing proof that involves a real can be reported, so a second-solver check of
  Dafny programs over reals cannot see any failure.

## 2. Dafny: `/enhancedErrorMessages:0` overridden when counterexamples are bound

- **Project:** github.com/dafny-lang/dafny, 4.11.0.
- **Measured:** the same run. Binding the counterexample option sets `EnhancedErrorMessages = 1`, so the flag that
  would avoid model parsing cannot be turned off. CVC5 also refuses `produce-models=false` after initialization, so
  there is no other way around issue 1.
- **Minimal reproduction to confirm:** `dafny verify --solver-path cvc5 /enhancedErrorMessages:0` with the file from
  issue 1. Check whether the option takes effect.

## 3. GNATprove with Z3: monotonicity of rounding not found

**Withdrawn 2026-10-07 (PREDICT T58):** rate_limit proves under Z3 at 200,000 steps. The timeout was the matrix's
20,000-step budget, not a missing lemma, so there is nothing to ask upstream.

- **Project:** github.com/AdaCore/spark2014. A question, not a bug.
- **Measured:** PREDICT T49 (rate_limit). With `r = prev + step` (Long_Float, `step >= 0`, all values bounded by 1e6),
  the postcondition `r >= prev - step` times out under `--prover=z3` at the matrix's step budget. It follows from the
  monotonicity of round-to-nearest.
- **Ask:** whether a lemma from SPARKlib's floating-point lemmas (`SPARK.Lemmas.Floating_Point_Arithmetic`) is the
  intended route, so t's SPARK lowering can cite it instead of timing out.

## 4. DafnyBench: specifications that admit a wrong program, with a Dafny proof of each

- **Project:** github.com/sun-wendy/DafnyBench (commit 0cd28fe).
- **Measured:** PREDICT T54, `t/AUDIT-DAFNYBENCH.md`, `t/dafnybench/CLASSIFIED.md`. In 44 of the 316 programs t lifts,
  Dafny proves a one-edit mutant that computes a different result at a stated input. 23 are gaps by reading. The
  clearest:
  - three `max` methods with `ensures c >= a && c >= b`, which admit `b + 1`;
  - a Euclidean division with no `0 <= r < b`;
  - task_id_397's median of three, which admits a non-median: `(0, 1, 0)` gives 1;
  - an `==>` precedence slip in cvs_projeto `m4`, which makes `z ==> x == y && x == y ==> z` a tautology;
  - the four dafny-synthesis specs MutDafny's authors named (task_id 2, 126, 161, 249).
- **Proved repairs ready** (PREDICT T61, `t/repairs/DAFNYBENCH.md`): 14 of the 23 gaps, as Dafny lines, each proved for
  the program as written with the mutant refuted.
- **Ask:** whether the maintainers want a list of strengthened `ensures` (each checked: the original body still
  verifies, and the mutant no longer does), or a note in the README that a verified solution may be wrong where the
  spec is weak.

## 5. vericoding: Verus specifications satisfied by wrong solutions, two by a constant

- **Project:** github.com/Beneficial-AI-Foundation/vericoding.
- **Measured:** PREDICT T56, `t/AUDIT-VERICODING-VERUS.md`, `t/vericoding/CLASSIFIED.md`. In 14 of 55 Verus tasks t
  lifts, Verus proves a one-edit wrong solution against the task's specification. 13 are gaps by reading:
  - The APPS-derived `va` specs state that the output is well formed. va0216 accepts any of R/P/S and va0654 any of
    A/B/C, so a constant solves each.
  - The NumPy-derived `vt` specs state mostly the output's length (vt0329 `log`, vt0496 `legmul`).
- **The Dafny track** (PREDICT T59, `t/vericoding/CLASSIFIED-DAFNY.md`): Dafny proves a one-edit wrong solution in 39
  of 425 verified tasks; 31 are gaps by reading, one spec is the tautology `len(result) >= 0` (da0417), and several
  APPS-derived specs pin only the YES answer (da0483, da0623).
- **Input-blind successes** (PREDICT T61): 13 of the 509 Dafny solutions and 8 of the 63 Verus solutions never read a
  parameter. `vericoded/verus/VA0216_vericoded.rs` returns `'R'` for every input; its spec defines `winner` and never
  uses it.
- **Proved repairs ready:** `t/repairs/VERICODING-DAFNY.md` and `t/repairs/VERICODING-VERUS.md`.
- **Why it matters for the benchmark:** a vericoding success is a kernel-verified solution, so these tasks count a
  wrong solution as a success. The paper's own manual estimate is that about 9% of specs are too weak; this is a
  mechanical lower bound with a proof per case.

## 6. Why3: Alt-Ergo's "2.4.3-free" version string is not recognised

- **Project:** gitlab.inria.fr/why3/why3 (1.8.2), or opam's alt-ergo-free package.
- **Measured:** the container build (`.github/workflows/container.yml`, run on 2026-10-07). `why3 config detect`
  registers alt-ergo-free 2.4.3 with an empty version, under drivers that emit Alt-Ergo 2.6 input (`.psmt2`). Every
  goal Frama-C/WP's Qed leaves open then reads `Failure`. An explicit `[prover]` stanza with `version = "2.4.3"` and
  `driver = "alt_ergo"` fixes it.
- **Minimal reproduction to confirm:** a fresh opam switch with `why3.1.8.2` and `alt-ergo-free.2.4.3`, then
  `why3 config detect` and `why3 config list-provers`.

## 7. Frama-C/WP: a frame fact for a recursive logic function over memory (a question)

- **Project:** git.frama-c.com/pub/frama-c (33.0).
- **Measured:** PREDICT T55. A loop invariant `r == pos{Here}(s, s_n, i)`, where `pos` is a recursive
  `\list<integer>` logic function reading `s`, steps out on preservation at 1,000,000 Alt-Ergo steps, although the
  loop writes only `r` and `\separated(s, r)` is required. double_all has the same shape.
- **Ask:** whether a `reads s[0 .. n - 1]` clause on the logic function is the intended route to the frame fact.
