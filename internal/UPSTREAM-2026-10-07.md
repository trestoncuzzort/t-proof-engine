## 1. Boogie: `BadExprFromProver` on a CVC5 model that holds a Real value

- **Project:** github.com/boogie-org/boogie (as shipped in Dafny 4.11.0).
- **Measured:** PREDICT T22 (2026-10-07), receipt 04b99488c420. Running Dafny's verification with `--solver-path` set
  to CVC5, any failing proof whose model contains a real-typed value aborts with `BadExprFromProver` before reporting
  a verdict. The model text is CVC5's `0.0`.
- **Cause, as read:** the model converter has no case for a Real constant in CVC5's model syntax (Z3 prints reals as
  `(/ 0.0 1.0)` or an integer form that the converter does handle).
- **Minimal reproduction to confirm:** a Dafny method with a `real` parameter and a false postcondition, verified with
  CVC5. Expected: an error "postcondition might not hold". Observed: the exception.
- **Why it matters:** with CVC5, no failing proof that involves a real can be reported, so a second-solver check of
  Dafny programs over reals cannot see any failure.

## 5. vericoding: Verus specifications satisfied by wrong solutions, two by a constant

- **Project:** github.com/Beneficial-AI-Foundation/vericoding.
- **Measured:** PREDICT T56, `t/AUDIT-VERICODING-VERUS.md`, `t/vericoding/CLASSIFIED.md`. In 14 of 55 Verus tasks t
  lifts, Verus proves a one-edit wrong solution against the task's specification. 13 are gaps by reading:
  - The APPS-derived `va` specs state that the output is well formed. va0216 accepts any of R/P/S and va0654 any of
    A/B/C, so a constant solves each.
  - The NumPy-derived `vt` specs state mostly the output's length (vt0329 `log`, vt0496 `legmul`).
- **The Dafny track** (PREDICT T59, `t/vericoding/CLASSIFIED-DAFNY.md`): Dafny proves a one-edit wrong solution in 39
  of 425 verified tasks; 31 are gaps by reading, one spec is the tautology `len(result) >= 0` (da0417), and several
  APPS-derived specs pin only the YES answer (da0483, da0623).
- **Input-blind successes** (PREDICT T61): 13 of the 509 Dafny solutions and 8 of the 63 Verus solutions never read a
  parameter. `vericoded/verus/VA0216_vericoded.rs` returns `'R'` for every input; its spec defines `winner` and never
  uses it.
- **Proved repairs ready:** `t/repairs/VERICODING-DAFNY.md` and `t/repairs/VERICODING-VERUS.md`.
- **Why it matters for the benchmark:** a vericoding success is a kernel-verified solution, so these tasks count a
  wrong solution as a success. The paper's own manual estimate is that about 9% of specs are too weak; this is a
  mechanical lower bound with a proof per case.

## 8. PX4: collision prevention's obstacle-map index goes negative for a wide field of view

- **Project:** github.com/PX4/PX4-Autopilot, at `dd804e4b9c490aed051bb36f8d3fca1ee137be2a` (main on 2026-10-07).
- **Route, by PX4's own policy:** SECURITY.md says a finding made with AI assistance is public from the start. It
  should go to a pull request with a fix, or to an issue if no open pull request covers it. SECURITY_SCOPE.md puts
  memory faults reachable only from an unsecured MAVLink link or a peripheral out of security scope, so this is a
  robustness bug, not an advisory. The reproducer stays out of the public text; the impact is described.
- **Measured:** PREDICT T68. `t/flight/px4_wrap_bin.t` proves `ObstacleMath::wrap_bin(bin, bin_count)` returns an
  index in `[0, bin_count)`, congruent to `bin`, whenever `bin >= -bin_count`. `t/flight/findings/px4_wrap_bin_any.t`
  drops that bound, and the kernels refute it. PX4's own `wrap_bin`, compiled, returns -1 at `(-73, 72)`.
  PX4's own test `ObstacleMathTest.WrapBin` states the intended contract: a negative bin is "wrapped back to the
  end" (-1 to 71). It checks no bin below -72.
- **Where the bound is not established:** `CollisionPrevention::_addDistanceSensorData`
  (src/lib/collision_prevention/CollisionPrevention.cpp:404) wraps every bin from
  `round((yaw_deg - degrees(h_fov / 2)) / BIN_SIZE)` up, and indexes `_obstacle_map_body_frame.distances`,
  `_data_timestamps`, `_data_maxranges` and `_data_fov` (72 entries each) with the result. `h_fov` comes from
  `distance_sensor`. The MAVLink receiver copies `horizontal_fov` without a range check
  (src/modules/mavlink/mavlink_receiver.cpp:1160). For a forward sensor, any `h_fov` above about 12.65 rad gives a
  negative index, and a value given in degrees (for example 30) gives 99 negative indices across the loop. A
  non-finite `h_fov` reaches `(int)round(...)`, which is undefined behaviour.
- **Proposed fix (two lines of defence):**
  1. `wrap_bin`: `int r = bin % bin_count; return r < 0 ? r + bin_count : r;` is a true modulo for every `int`
     `bin` and positive `bin_count`. The t proof carries over: drop `requires bin >= -bin_count` and the contract
     holds.
  2. `_addDistanceSensorData`: skip the sample unless `PX4_ISFINITE(h_fov)`, and constrain `h_fov` to
     `[0, 2 * M_PI_F]` before computing the bounds. This also caps the loop at `BIN_COUNT + 1` bins.
- **State (2026-10-08):**
  - The patch is committed on a local branch of a PX4 checkout (`fix/collision-prevention-wrap-bin`). It touches
    five files.
  - Its message follows PX4's conventional-commit rule and carries the `Assisted-by:` trailer PX4's
    AI-assistant policy requires.
  - PX4's own `ObstacleMathTest` passes 6/6 with it and fails on the old code (-1 for `wrap_bin(-73, 72)`).
  - `t/flight/fixes/` proves the fixed function: in six kernels at 72 bins (SPARK open), and in SPARK, Frama-C
    and F* for any bin count. `px4_diff.py --fixed-tree` finds the patched PX4 code agreeing on every point.
  - Still to run: PX4's full `make tests` and `make check_format`.
  - PX4 requires the human submitter to review every line before submitting.
  - Open PR #27826 (body-frame obstacle loop) is a separate bug in the same module, found by someone else.
- **Before filing:** search the open pull requests for an existing fix. Then rerun `px4_diff.py` on the main of that
  day. A PR with a unit test in `ObstacleMathTest.cpp` (for example `wrap_bin(-73, 72) == 71`) is the form PX4 asks
  for.
